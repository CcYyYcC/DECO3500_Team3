# Final Firmware Provenance, Change Scope, and Validation Notes

## How the final version was assembled

This package is **not a complete rewrite** of the earlier project. The final firmware was assembled through **small, defined changes to existing complete `.ino` sketches**:

1. **Three personal Tokens:** The source for all three complete sketches was `TimeTokens_FullScreen_Progress.zip`. The sketches retain DemoCycle v3's ESP-NOW final ACK, round synchronisation, checkmark/return-arrow feedback, eight-second full 64-LED progress, and other display states. The call inside `showProgress()` was changed from the pre-rotation `maxWrite(8 - i, 0xFF);` to **`maxWrite(1 + i, 0xFF);`**, producing the 180° orientation required for viewing a flipped Token. No other behaviour was intentionally changed in that merge.
2. **Tower ESP32:** The complete file `TimeTokens_DemoCycle/Tower_Bridge_DemoCycle/Tower_Bridge_DemoCycle.ino` was retained **without changing its program contents**.
3. **UNO R4:** The base file was `TimeTower_Breath5s/R4_DemoCycle_Breath5s/R4_DemoCycle_Breath5s.ino`. The five-second green → blue → red breathing effect, 10-second scene hold, UART format, and round protocol were retained. The only intended code change was setting **`BRIGHTNESS` from 70 to 20**, based on the latest reported physical observation.

Each complete sketch was copied into its own folder with a matching `.ino` filename so it can be opened independently in Arduino IDE without overwriting older revisions.

## Why use brightness 20 on the final R4?

Physical testing indicated that at brightness 70 the entire 256-pixel WS2812B panel showed random colours, including the separator columns that should have been black. The user reported that the behaviour stopped after reducing brightness to 20. This **observed comparison** supports using brightness 20 for a classroom demonstration but does not establish that “the power supply is completely safe” or that one definitive root cause has been found.

## Why keep all 64 progress LEDs on the Exercise Token?

The Exercise Token previously went black when only the last two or three rows remained to be filled. It later ran normally during a standalone USB-C power-bank test, while the Gaming Token had already been operating normally. These observations are not sufficient to prove that the row-by-row full-screen algorithm itself is faulty. We therefore kept the intended **complete 64-pixel fill** and documented power delivery, wiring, module differences, and multi-device operation as outstanding checks.

## Checks performed on the merged firmware baseline

- Retrieved and assembled all five complete `.ino` files from the existing local baselines.
- Checked that the three Tokens use separate `TOKEN_ID` values (1/2/3) and corresponding activities (EXERCISE/STUDY/GAMING).
- Checked `DURATION=8000`, `RETURN_SWAP_MS=800UL`, the inverted row sequence in `showProgress()`, and preservation of completion feedback and final ACK logic.
- Checked the key R4 settings for brightness 20, five-second breathing, 10-second simulation interval, 10-unit left-side capacity, and 10-second hold.
- Checked that the Tower ESP32 source matched the original DemoCycle v3 source byte-for-byte.
- Performed basic static checks of C++ text structure, balanced delimiters, Arduino `setup()`/`loop()` presence, and the progress-row register range.

**Checks not performed:** No Arduino IDE or hardware-target compilation, new firmware upload, complete multi-board endurance test, or physical power measurement was conducted for this merged release. Older host-side assertion tests reported in project conversations are **not** claimed to have been rerun on these exact integrated files. This is a **current uploadable source baseline**, not production-certified code.

## Differences between early design specifications and current firmware

- Button confirmation, saving unit counters through power loss, and several other ideas in `TIME_TOKEN_CONCEPT_SPEC.md` were **proposed features**, not a complete description of the current implementation.
- Early `FinalACK` and `DropDone` examples used a 10-byte ESP-NOW data packet and a 16-byte ACK. These **cannot be mixed** with the current 32-byte DemoCycle v3 protocol.
- GPIO45 remains reserved for a vibration motor. This package does not claim that vibration feedback has passed real-device testing.
- The right-side simulated player is generated by the R4 script; it is not a fourth real Token or a second participant's actual record.
